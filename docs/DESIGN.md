# 设计说明

## 1. 分层与数据流

```
合成信封 JSON ──ingest──▶ Store（不可变信封 + 事件日志，JSON 原子写）
                              │
                              ▼
                         Registry（纯派生只读视图：当前版本 + 完整历史）
                              │
            ┌─────────────────┼──────────────────────┐
            ▼                 ▼                      ▼
       PolicyBook        EvaluationEngine       HouseholdLedger
      （按日期选版）    （材料/票据/金额/额度）   （从有效决定派生）
                              │
                              ▼
                       Workbench 门面
        decide / pay / withdraw / review_queue / trace / applicant
```

所有可变状态只有 Store 里的信封与事件；Registry、Engine、Ledger 都是无状态派生，
同一份存储可以随时重建出完全一致的视图。

## 2. 关键建模决策

### 2.1 信封不可变，附件按业务键版本化
- 发票业务键为 `(receipt_id, application_id)`：同一张发票提交给不同申请会形成两条引用，
  这正是重复提交检测所需的结构。
- 同一业务键下的信封按 `revision` 排序，最新版为当前视图，旧版保留在 `history` 中；
  `state=withdrawn` 表示撤回。住房证明同理。
- 摄入按 `source_id` 去重，重复投递整批跳过，保证可持续、可重放。

### 2.2 政策版本与「提交时/决定时」双版本
- `PolicyBook.rule_effective_on(city, d)` 返回日期 `d` 当天已生效的最新版本。
- 评估同时给出提交时版本与当前版本：版本不同 → `POLICY_CHANGED` 提示；
  当前版本取消该用途 → `USE_NOT_ELIGIBLE` 硬性问题。
- 政策调整不回溯已付款项目：付款是终态，决定里冻结的政策快照永不重算。

### 2.3 额度双轨
- **家庭年度上限**：`(household, year, use)` 维度，台账条目来自每个申请的**最新有效
  批准决定**（含已批待付与已付款）。旧批准被后续决定拒绝/撤回时自动退出，无需手工冲账。
- **个人账户余额**：成员静态属性，只参与单条申请的可批准额计算。
- 可批准额 = min(申请额, 有效票据合计, 家庭剩余上限, 个人账户余额)。
  上限/余额不足是 warning（可部分批准），材料类问题是 blocker（不能批准，特批需 `--force` 留痕）。

### 2.4 终态与重审队列
- 终态：`paid` / `rejected` / `withdrawn`。终态申请不进重审队列、不能改判、不能重复付款。
- 重审队列分两类派生：
  - policy_driven：未结申请的提交时政策版本 ≠ 当前版本（如 AP-86）。
  - material_driven：未结申请关联的发票/证明存在多版本（更正）或撤回（如 AP-85、AP-89）。
    已批待付不是终态，材料变化仍须重审。
- 材料失效本身**不**自动回滚额度：额度由决定驱动，只有审核员对该申请作出新决定后，
  下一次台账重建才改变占用。其他成员的已用额度因此不会被一件材料失效错误释放。

### 2.5 历史保真：付款先于审批的补录
- 基线数据中 AP-81 只有付款信封没有决定信封。摄入付款时系统按**付款当日生效政策**
  补录一条 `system-backfill` 批准决定。
- 补录快照使用时点视图（`as_at=付款回执 collected_at`）：11 月 15 日才撤回的发票，
  不会污染 10 月 11 日付款决定的证据清单，快照冻结的是 rev.1 active 版本。

### 2.6 证据哈希与可追溯
- 每个证据信封的 payload 经规范化 JSON（排序键、无空格）后取 SHA-256 前 16 位，
  写入决定快照。`trace <申请号>` 可以从决定一路看到政策版本、证据版本/状态/哈希，
  以及发票的全部更正历史信封。

## 3. 合成数据覆盖的场景（fixtures/sources.json，39 信封 / 11 申请）

| 申请 | 场景 | 预期结论 |
| --- | --- | --- |
| AP-80 | v3 期间批准并付款，v4 取消购房 | 终态 paid，保留 v3 依据，不进重审 |
| AP-81 | 付款先到触发补录；发票事后撤回且被 AP-84 重复引用 | 终态 paid；补录快照冻结 rev.1；实时评估报撤回+重复 |
| AP-82 | 缺物业费发票（后补批次可补齐）；家庭上限被 AP-83 占满 | 缺材料 blocker；补齐后仍因额度为 0 只能部分批准 |
| AP-83 | 申请 6500 超家庭上限 6000 | 无 blocker，CAP_PARTIAL，可批 6000 |
| AP-84 | 重复使用 AP-81 的发票 | RECEIPT_DUPLICATE + RECEIPT_WITHDRAWN |
| AP-85 | 发票被撤回 | RECEIPT_WITHDRAWN，进材料重审队列 |
| AP-86 | v3 期间提交购房，v4 取消该用途 | USE_NOT_ELIGIBLE + POLICY_CHANGED，进政策重审队列 |
| AP-87 | CITY-B 6 个月窗口外的物业费发票 | RECEIPT_OUT_OF_WINDOW；`--as-of` 回溯可消除 |
| AP-88 | 家庭上限 3000 但成员余额仅 2000 | BALANCE_PARTIAL，可批 2000（双轨额度） |
| AP-89 | 发票更正 3000→2800，已批待付 | 进重审队列；特批金额仍被约束为 2800 |
| AP-90 | 引用非本人/非本家庭的住房证明 | HOUSING_MISMATCH |

## 4. 安全与运行约束

- 资料目录 `fixtures/` 视为不可信输入：每个来源批次放在独立目录，解释器从不在其中运行，
  资料目录不加入 `sys.path`；运行期数据写入 `data/`（已 gitignore）。
- 统一以 `python3 -I` 运行：隔离模式忽略 cwd 与 PYTHONPATH，`run_workbench.py`
  仅注入基于 `__file__` 的可信代码目录，并在路径注入前预载标准库，防止同名模块遮蔽。
- 无第三方依赖，全部基于 Python 3.11 标准库。
